1. Purpose, scope and golden rules

This suite checks the iFlowCKYC 4.0 web application end to end through the browser. It is a hybrid BDD framework: tests are written as Cucumber scenarios, but every check, locator and report is handled in plain Java layers so a new engineer can find any behaviour in one place.

The application is a live product. The suite is therefore written to read, compare and, where it creates data, to create only clearly marked test data and to leave the application as it found it.

Golden rules (read these first)

RuleWhat it means in practice
Live product - touch only test dataCreate, edit or delete only records whose name starts with TEST / TEST AUTO / testauto. Never edit seed users, Super Admin, or existing masters. DVS suites restore the record after every row and stop if the restore cannot be verified.
One browser tab, one sessionThe application refuses to run if it is open in another tab on the machine, and a second login logs the first out. Before the browser starts, the framework closes other iFlowCKYC tabs (not your report tabs). Never open the app manually while a run is going.
Navigation bar firstAlways find and click the side-navigation item like a user. Use a direct URL only as a fallback when the nav item is missing or did not land on the page. This applies to every module.
No credentials in codeLogins come from config.properties and TestData/user-management.properties. Do not hard-code or paste passwords in code, features, logs or tickets. Do not commit config.properties.
Soft assertionsA failed check is recorded and the scenario continues, so one run shows every defect. The scenario is marked failed at the end. Only a missing prerequisite or a stop request ends a scenario early.
A missing expected message is a bugIf an action should show a toast and none appears, the result is reported as a BUG, not silently passed.
Evidence for every resultEvery failed check has a screenshot. Key steps also have passing screenshots. Reports show "Tested by" the engineer named in testedBy.
Locators: verified, role-basedPrefer aria-label, role, data-testid and visible text. Verify a locator against the live page before it goes into a Page class.
Do not drive Search or DVS by hand tools while a run is activeDebugger tools attached to the browser changed the application's behaviour once. The Selenium runner is the test of record.

2. Quick start

2.1 Prerequisites

  • Windows machine (the existing-tab closer uses Windows UI Automation; the rest is portable).
  • JDK 21 and Maven 3.9+; IntelliJ IDEA (any recent version).
  • Google Chrome (the driver is downloaded automatically by WebDriverManager).
  • Network access to the application URL in config.properties and a working login for the Maker user.

2.2 First run

  1. Open the project folder in IntelliJ and let Maven import dependencies.
  2. Open src/test/resources/config.properties. Set url, username, password, browser=chrome, testedBy. All other keys have defaults (see section 5; the documented list is config.properties.example).
  3. Close any open iFlowCKYC browser tab.
  4. Run TestRunner/TestControlPanelRunner (right-click, Run as TestNG). Chrome opens on the login page and the Test Control Panel pop-up appears.
  5. Choose the type of testing (Positive / Negative / Both), tick the modules, press Start Test. The run continues in the same browser.
  6. When the run ends the Advanced report, Extent report and Cucumber report open automatically.

Any single-module runner (for example TestSearchRunner) shows the same panel, pre-ticked with that module. To run without a human present set headless=true (or interactiveBlockerPrompt=false): the panel and the pop-ups are skipped and the runner's default tags are used.

3. Architecture and code layout

Figure 1 - Layers. Code flows downward; each layer knows only the layer below it.

3.2 The two funnels

Hooks.runStep(description, expected, action, captureOnSuccess, mandatory) - every step definition runs its action through this method. It: records the step context (feature, scenario, step) for pop-ups; skips the step if a stop or skip was requested; runs the action inside the blocker handler; on an exception detects a server-error page, tries one safe refresh and retry, and if the step is mandatory and the failure looks like "element missing" shows the decision pop-up; otherwise records a soft failure with a screenshot.

StepLog.check(scenario, step, expected, actual, passed, testData) - every business check reports through this single method. It writes the row to Excel, Extent and the Advanced report, and a failed check becomes a soft assertion failure. Never use a raw assert inside a Functionality class.

4. How one test run works

Figure 2 - Run lifecycle.

4.1 Selection to execution

  1. Start: RunnerSuiteSupport.beforeSuite closes other app tabs, launches Chrome, opens the login page.
  2. Panel: the Test Control Panel returns the selection. ControlPanel.apply sets the JVM properties cucumber.filter.tags and cucumber.features (all feature folders) and any ckyc.<key> overrides before Cucumber lists the scenarios. This is why a single-module runner can run other modules.
  3. Order: CkycCucumberTests.scenarios() re-orders the chosen scenarios with ExecutionOrder: Login, Dashboard, State, District, Pincode, Hierarchy, Search, Search interactive, Roles (positive, negative), Users (positive, negative), DVS Individual, DVS Legal, DVS workbook runs, Reports, Concurrent session last (it signs the first session out). Positive runs before Negative inside a module. Without the panel the order is Cucumber's own (folder name).
  4. Scenarios: @Before starts the Extent test and the Advanced report scenario, applies skip/abort flags; steps run; @After checks the final page, flushes soft failures, closes the scenario record.
  5. End: @AfterSuite generates all reports, opens them, waits suiteCompletionWaitSeconds on the completion prompt, logs out and closes the browser.

4.2 "Already logged in" rule

Every feature starts with user is logged in and on CKYC dashboard. AppSession.isInsideApp decides whether to resume or to log in: the URL is not /login and is the dashboard, /ckyc/ or /admin/, or any other page of the same host with a real path and no login form on screen. If inside the app the step only goes to the dashboard (via the nav bar) and checks the filter bar. Otherwise it performs the login steps.

4.3 Scenario status

StatusWhen
PassedNo soft failure recorded and no skip/abort.
FailedAt least one failed check or step. All steps were still executed.
SkippedThe user chose Skip this case / Skip this feature, or a mandatory prerequisite blocked the feature ("Stop module").
AbortedThe user chose Stop everything. The browser is closed, reports so far are written, every remaining scenario is aborted.

7. Pop-ups, recovery and retries

7.1 The decision pop-up

When a mandatory step cannot find an expected page, button or field, or a blocker stops the next action, the framework draws a pop-up on the page. It names exactly where the automation is, so you never have to read a stack trace:

RowContent
Feature / Scenario / StepWhere the run is.
ExpectedWhat the step expected to see.
FunctionalityClass and method that was running (from the failing call stack).
Step definition / Page objectThe glue method and the Page class involved.
Element / locatorThe locator that was not found, extracted from the Selenium message.
What happenedShort error and the page currently open.
ButtonEffect
Continue / RetryFix the page by hand first (log in, open the right page, close a dialog), then click: the same step runs again right away. Up to 3 tries; each new failure asks again.
Skip this caseThe scenario is marked skipped; the next scenario of the same feature runs.
Skip this featureThe rest of the feature file is skipped; the next feature / module chosen in the panel still runs.
Stop everythingThe whole automation ends: all remaining scenarios, features and modules are cancelled, reports so far are written, the browser closes.
No answer in 60 sTreated as Skip this case. A live countdown is shown.

7.2 When the pop-up appears

  • The step was declared mandatory (the last argument of runStep) and the failure looks like "element missing" (NoSuchElement, timeout, "not found") - or a server-error / foreign page is detected (HTTP 500 etc.). Optional checks never raise the pop-up; they record a soft failure.
  • Before the pop-up the framework already tried one safe refresh and a retry of the step.
  • A click blocked by an application dialog (SweetAlert, overlay) uses the same pop-up with the button named Retry. A short invisible MUI backdrop is handled silently (Escape, wait, retry once).
  • A module that cannot create its mandatory record raises the same four answers as a module blocker.

7.3 Retries and session loss

  • Scenario retry: maxScenarioRetries=1, only for Login, Dashboard, Search, Masters tags.
  • If the browser window disappears ("invalid session id") the module stops cleanly with SessionLost; Reports compare writes its workbook anyway and records STOPPED with the reason.
  • Active-session dialog after login: the framework clicks "Log out other session and continue". Chrome's password / breach bubble is dismissed with Escape after login.

DecisionAccepted when ANY of these is true
ApprovedToast contains approved or success; or neither the Approve nor the Revert icon remains on the row; or the row is in the Approved queue (status dropdown = Approved). Blocked (negative)The Approve icon is not present; or the browser is sent to /login (reported as BUG-001: no toaster); or the toast is a rejection (self: maker / own / not allowed / cannot / self; same-role: same role / role + cannot / not allowed / checker); or the toast does not say approved / success. Fails only when an approved / success toast appears.
Details verifiedView Details text contains the login, the Maker name, the request type (create / edit-update / lock / unlock / dormant) and the status; for Approved / Reverted also the checker's name (first 4 letters accepted).
NavigationNav bar: open menu, User Management, Users or Roles. Not on /admin/users or /admin/roles afterwards = direct URL. Session returned to login for a Checker = FAIL "Session returned to login".

Known weak points of these rules (agreed to review): "success" also matches "unsuccessful"; icons disappearing may be a refresh; negative checks pass when nothing happens; the same-role negative assumes admin and automaker share a role; the dormant check passes when the row merely exists; later steps still run after a failed approval; the toast is read for 3 s only. Tighten these with the exact application messages before relying on a negative result.

10. Adding a new module: checklist

  1. Find it through the nav bar; add a nav locator in pages/SideNavPage (module and sub-module builders already exist). Use the URL only as a fallback.
  2. Page class pages/<module>/<Name>Page.java: locators only. Verify each against the live page (aria-label, role, data-testid, visible text).
  3. Functionality class functionality/<module>/...: the journey and every check through StepLog.check. Use MasterUiHelper and ToastHandler; explicit waits only. Create only TEST data and restore anything you change.
  4. Step definitions stepdefinitions/<module>/...: wrap each action in Hooks.runStep(description, expected, action, captureOnSuccess, mandatory). Make a step mandatory only if its failure means the rest of the scenario cannot run.
  5. Feature under Features/<n>_<Module>/ with a Background user is logged in and on CKYC dashboard and tags: module tag, @Positive / @Negative, @Smoke. Use @Deferred for work not ready.
  6. Runner TestRunner/Test<Module>Runner.java extending CkycCucumberTests; call RunnerSuiteSupport.beforeSuite/afterSuite like the others; own JSON file name in target/cucumber.
  7. Control Panel: add one entry to ControlPanelRegistry (key, title, sub-modules with positive / negative tag, option groups, text boxes) and the tag to ExecutionOrder.TAG_ORDER at the right place.
  8. Config: new keys go through ConfigReader with a default and a commented line in config.properties.example.
  9. Report: nothing extra is needed - StepLog.check and the hooks feed every report. Add a module workbook only if the data is large.
  10. Prove it: compile, dry-run Cucumber with the tag (cucumber.execution.dry-run via a runner), then one live run; update this guide's module section.

11. Coding conventions

  • File header on every Java file: CKYC 4.0 Automation Framework - Author: Aravindhan - Created and developed by Aravindhan. Package root Com.Ckyc_4_0.
  • Match the surrounding code: tabs, naming, comment density. Comments explain why, not what.
  • One responsibility per layer (section 3). A Page class never calls the driver; a step definition never contains a condition.
  • No Thread.sleep for synchronisation except in MasterUiHelper.sleep for very short MUI settle times; prefer explicit waits. Implicit wait stays 0.
  • Never swallow an exception silently in a check. If a failure is expected and handled, log why.
  • Check messages follow the pattern: scenario ("Module | check"), step, expected, actual (with key values), passed, test data.
  • Locators: aria-label, role, data-testid, stable visible text. Avoid index-based and class-hash xpaths. Dropdown options are selected by visible text prefix.
  • Do not hard-code data that the page can tell you (dashboard sub-cards, report types, document types).
  • Test data lives in TestData/ (properties, CSV, Excel) and is documented next to the file.
  • Generated and secret files are not committed: config.properties credentials, Report Output, target, logs.
  • Verifying without Maven: compile the changed files with javac against the Maven repository jars, then dry-run Cucumber for tag and feature selection before a live run.
